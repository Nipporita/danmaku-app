# danmaku-app · 元火互动环节

弹幕驱动的现场互动游戏（`fourth_righter`）：选手在 QQ 群里报名、答题，观众在群里打分，
大屏实时同步。

大屏页面不是单一 HTML：`index.html` 会把站点模板 `template.html` 与游戏页
`fourth_righter.html` 合并成一个文档，再按顺序注入两边的脚本，最后连上弹幕后端
（ne-danmaku）的 WebSocket，收弹幕、发指令。

```
QQ 群 ──▶ LLBot(Satori) ──▶ ne-danmaku ──WebSocket──▶ 大屏游戏页（本仓库）
```

## 目录

| 路径 | 说明 |
| --- | --- |
| `danmaku-frontend/` | 大屏游戏页：`fourth_righter.{html,js,css}`、问题池、站点模板、开发服务器 |
| `danmaku-frontend/fourth_righter_questions.js` | 主观问题池（**由出题 docx 生成**，见下） |
| `tools/docx_to_questions.py` | 把「主观题出题」docx 转成问题池 |
| `danmaku-server/server.py` | 本地弹幕模拟器（Tkinter + WebSocket），彩排用 |

## 观众贴表情（直播感）

**任何人在群里给某条答案消息贴表情**，大屏上就会有**一模一样的那个表情**从**那张答案卡上的
答案上方**"长出来"，往上飘走、淡出**。回答期间和打分期间都会飞（答案一直挂在选手卡上）；
主持人的审核也走这条路（审核成功时屏上会飞一个他贴的表情，顺便就是反馈），观众的附和同样会飞。

- **锚点只认选手卡上的答案**（不是打分环节左边那排"答案条"）。没抽到上场、待机/报名阶段
  没有卡，或者消息根本不是答案 → **不放**。
- 取消表情（`action: "remove"`）只关闸，不飞表情。
- 同时最多 **14** 个（`fourth_righter.js` 的 `REACTION_FLY_MAX`）：QQ 里表情能连点，防刷屏糊屏。
- 表情**图**用 Twemoji（jsDelivr，和站点其它资源同一个 CDN）；拿不到图就退回直接渲染字符，
  所以现场网络受限也能显示。浮层 `#reaction_fly_layer` 是 `pointer-events: none`，绝不挡点击。
- 想调手感：尺寸/时长在 CSS 的 `.reaction_fly` 与 `@keyframes reaction_fly_out`，
  飘的方向和距离在 JS 里设的 `--fly-x` / `--fly-y` / `--fly-rot`。

## 题库与出题人

题目来自社团的**出题 docx**（`主观题出题.docx`），格式是每行 `题目正文（出题人）`：

- 出题人写在**最后一对**括号里，取出来单独存 `by` 字段，大屏上显示成题目下方一行
  「出题人：xxx」（只在**答题环节**显示；打分环节的问题条只放题目本身）；
- 括号**后面**的内容（出题人的吐槽，如"战斗，爽 战斗，爽！"）一律丢掉；
- 代号会换成真名：`沙`→沙雕之歌、`chi`→chilian、`亭`→无木亭、`N`→Nipporita、`F`→Flying Craft
  （星、玄咒、薜荔等本来就写全名的原样保留）；
- 题目正文里**本来就有**的括号会保留：`最有冲击力的动漫名场面（/台词）（沙）`
  → 题目 `最有冲击力的动漫名场面（/台词）`，出题人 `沙雕之歌`。

重新生成题库（拿到新 docx 后跑一遍就行）：

```bash
python tools/docx_to_questions.py "D:\Downloads\主观题出题 (1).docx"
# 也可以显式指定输出：... "主观题出题 (1).docx" danmaku-frontend/fourth_righter_questions.js
```

**大屏按 3904×672 设计**（超宽矮）。题目太长会自动缩：先降字号，降到底再整块等比缩放，
答题环节的白框和打分环节顶部的问题条都适用；窗口尺寸变化 / 字体加载完成后会重新量一次。
所以长题目（如《BanG Dream! Ave Mujica》那道）在两个环节都不会被 `overflow: hidden` 切掉。


## 现场流程

主持人在群里发**控制词**推进流程；选手在群里扣 1 报名，被抽中后上场答题，观众发数字打分。

| 控制词（群里发） | 作用 |
| --- | --- |
| `开始报名` | 进入报名环节，清空上一局的选手席 |
| `开始游戏` | 开赛（若报名进度还没满，就先抽选再开赛） |
| `开始打分` | 停止答题，进入观众打分 |
| `结束打分` | 结算本回合分数，进入回合间歇 |
| `下一回合` | 换题，回到回答环节（打分阶段不允许） |
| `结束游戏` | 结束整局，记入「已玩过」，回到待机 |

主持人元指令（仅主持人、仅特定阶段生效）：

| 指令 | 作用 |
| --- | --- |
| `/set N` | 设置上场人数（N 取 1~6，实际夹到 4~6；仅待机/报名阶段） |
| `/remove i` | 去掉第 i 个玩家（报名=取消报名；回答/停止回答=退赛删除） |
| `/clear i` | 清掉第 i 个玩家的答案（回答/停止回答，防弹幕事故） |

控制面板（页面左上角「控制面板」展开）另有：添加玩家、清空已玩过、重置题库、
`主持人昵称`输入框、`答案需审核`开关、上面 6 个控制词的按钮、测试弹幕开关。
面板上的按钮等同于主持人本人在群里发言。

## 四条容易踩的规矩

1. **身份以 QQ 号为准，昵称只用来显示。** 一切数据都挂在弹幕的 `senderId` 上，
   所以比赛中改群昵称不会丢答案、不会重复投票，主持人改名也不会丢主持权。
   拿不到 `senderId` 的来源（本地模拟器、手工加的人）退化成 `name:<昵称>` 合成身份。
2. **主持人不能报名、不能被抽中、不能投票。** 主持权判定顺序：
   `is_admin`（群主/管理员，由后端下发）→ 绑定该 QQ 号；
   否则昵称与控制面板里填的一致**且说的是控制词**才绑定（防止有人把昵称改成 Admin 就夺权）。
   群里的**所有**群主/管理员都会自动成为主持人。
3. **答题要过审才算数（可在面板关掉）。** 选手答完后卡片是「待审核」（灰字），
   主持人**在群里给答案消息贴任意表情**才变「已通过」（绿 ✓）；
   **只有过审的答案会进入打分列表**。回答环节结束后、点「开始打分」之前贴表情同样有效
   （一条都没过审时会退回回合间歇并提示主持人先去贴表情）。
   **表情可以取消**（QQ 里撤掉那张表情）：取消 = 取消审核，卡片回到「待审核」。
   **任意表情都算过审**，而且用的是哪个表情会一起记下来（提示里显示 `✅ 👍 …`），
   表情图本身也能拿到（见文末帧契约里的 `emoji_char` / `emoji_url`）。
4. **一个选手说了多条答案：以他说的第一条为准**（回答顺序说了算）。
   主持人的表情只是"闸"——负责放行或取消，**不负责挑内容**，所以不存在"把答案换成另一条"
   的余地；给第几条贴表情都改变不了答案文本（贴第二条时会提示"本轮以他第一条答案为准"）。
   真要换答案，唯一的正当路径是**撤回第一条**（撤回是明示动作，撤回后第二条自动顶上，
   但审核状态随被撤回那条一起作废，需要重新贴表情）。
5. **撤回 = 这条答案没答过。** 选手撤回群里的答案消息后，大屏上那条答案被撤下、
   回到"未回答"；回答中、停止回答阶段都受理，**打分一开始就不再受理**。
   撤回**只影响被撤的那一条**：他还答过别的，屏上不会受影响。
   <br>**操作提醒**：回答环节里，上场选手的**任何**发言都会被当成答案，所以开始前跟大家说好
   "回答环节只发答案"。要是有人先发了闲聊，让他撤回那条（或主持人 `/clear i` 清掉他），
   否则那句闲聊就是他本轮的答案。

## 报名与抽选

- 报名池容量 = **上场人数 × 2**（默认 6 人 → 12 人）。先到先得，池满后其他人扣 1 会被忽略。
- **进度条走满即自动随机抽选**，N 张选手卡当场出现在大屏上（中选者在候选区反色标记）。
- 进度没满也可以点「开始游戏」提前抽选（至少 4 人）。
- 已经上过场的人**不会**再被抽中（面板「清空已玩过」可重开一局）。
- **人黑名单里的人是"影子封禁"：照常报名、照常出现在候选区，但永远不会被抽中、
  永远不上台**（对方察觉不到，大屏上也没有任何痕迹）。
  万一干净的人不足 N 个，就按实际人数开场——**宁可少人，也不让被禁言的人拿到话筒**；
  不足 4 人时点「开始游戏」会提示上场人数不足，可以用控制面板的「添加玩家」补人。
  影子封禁只决定"能不能上台"，**不影响计票**：黑名单的人投票照样算。
  判定依据是后端每条消息上的 `block_reasons` 是否含 `user_blacklist`，每条现算，
  所以解除禁言后自动失效。

## 落盘与恢复

整局进度存在浏览器 `localStorage`（键 `fantasyguide.fourth_righter.save.v1`），
包含：已玩过名单、出过的题、当前问题、状态机、报名池、选手与分数、答案、投票、
以及**倒计时截止时刻**。大屏崩溃或误刷新后 F5 即可回到原局面，倒计时接着走。

- 换一场活动重来：点「清空已玩过」+「重置题库」，或直接清掉浏览器里上面那个键。
- 题目跨局、跨刷新都不会重复；题库全部出过一遍后才会重新洗牌。

## 本地彩排（不用 QQ 群）

```bash
# 1) 起模拟弹幕源（端口与前端默认值一致，省得手填）
cd danmaku-server
python server.py 8000

# 2) 另开一个窗口起前端静态服务（禁缓存 + 改文件自动刷新）
cd danmaku-frontend
python dev_server.py 1919      # 或直接双击 server.bat

# 3) 浏览器打开 http://localhost:1919/ ，点「连接」
```

模拟器面板上除了控制词按钮，还有几个专门排练新功能的按钮：
**撤回最后一条答案 / 给最后一条答案贴表情 / 给第一条答案贴表情 / 取消最后一条表情 /
撤销最后一条答案 / 影子黑名单（把 Alice 加入或移出人黑名单）**。
点「开始报名」会一次灌满 12 个人（6 个固定选手 + 6 个随机观众），正好触发"进度满自动抽选"。

**排练游戏流程时先把面板上的「自动随机弹幕」勾掉**：模拟器会持续随机发弹幕，而上场选手的
随机发言在回答环节会被当成"答案"、随机数字在打分阶段会被当成"投票"，流程会被搅乱。
另外模拟器自己会跟着状态走：看到进入报名就灌一批扣 1、看到进入回答环节就灌一批答案 ✓

排练影子封禁：先点一下「影子黑名单: Alice」把她标记，再点「开始报名」——
她照常扣 1、照常出现在候选区，但无论抽几次都抽不到她；点第二次可解除。

## 现场注意事项

- **提前预热一次大屏。** `index.html` 是按顺序注入 CDN 脚本的
  （`cookie.js` → `template.js` → 游戏脚本，用 `onload` 串联）：链上第一个 CDN 脚本一慢，
  后面的游戏脚本就**永远不会执行**，而且不报错（现象：模板框架在、游戏没起来）。
  彩排当天先打开一次页面，让它把 CDN 资源缓存下来。
- **端口**：真实后端（ne-danmaku）默认 8000，前端「端口」默认也是 8000；模拟器默认 8080，
  用 `python server.py 8000` 起就不用改了。
- **`blocked` 弹幕照样参与游戏。** 后端只会给黑名单/去重命中的消息打 `blocked` 标记、
  不丢弃原始文本，游戏逻辑照常处理；`blocked` 只影响弹幕展示层。
  具体原因在后端的 `block_reasons` 里，三种分开：
  `user_blacklist`（发送者在禁止名单里，他的**所有**消息都被标记）、
  `word_blacklist`（这条消息的文本命中言论黑名单正则，只标记这一条）、
  `duplicate`（短时间内的重复内容，按房间隔离；当前配置 `dedup_window: -1` 时不会出现）。
  同一条消息可能同时命中多个原因。
  **游戏侧只用 `user_blacklist`**（做上面那条影子封禁）；`word_blacklist` 和 `duplicate`
  不影响游戏，票数和答案照算——避免观众发言被正则误伤时连带丢票。
- 后端会给"特殊弹幕"（管理端/上游发出）尾部补一个 👑，游戏层会先剥掉再匹配控制词。

## 与后端的帧契约

大屏连的是 `ws://<后端>/api/danmaku/v1/danmaku/<房间名>`，收到的帧：

```ts
// 弹幕
{ type: "plain" | "emote" | "multi_emote" | "superchat" | "gift",
  text, sender, senderId, message_id, is_admin, is_special, blocked, block_reasons,
  inline, text_plain, inline_only, ... }

// 控制
{ type: "settings", settings: {...} }
{ type: "control", action: "clear_all" }

// 游戏侧事件（由 ne-danmaku 的撤回 / 贴表情事件转成）
{ type: "recall",   message_id, sender_id, operator_id, channel_id }
{ type: "reaction", action: "add" | "remove", message_id, sender_id,
  emoji, emoji_char, emoji_url, channel_id, is_admin }
```

其中 `message_id` 必须与弹幕帧里的同源，撤回与贴表情才能对上"大屏上的哪条答案"。
`reaction` 的 `action` 区分贴表情（`add`，通过审核）和取消表情（`remove`，取消审核）——
上游对应 Satori 的 `reaction-removed` 与 OneBot 的 `is_add=false`。

**表情图也能拿到**：`emoji` 是上游给的表情 id。QQ 的「贴表情 / 回应」用的就是标准 emoji
那一套，**id 直接是 Unicode 码点**（128077 = 👍、128514 = 😂、128064 = 👀），所以后端顺手
把 `emoji_char`（可直接显示的字符）和 `emoji_url`（图片地址）一起下发：标准 emoji 走
Twemoji（`cdn.jsdelivr.net/gh/twitter/twemoji@14.0.2/assets/72x72/1f44d.png`，和站点其它资源
同一个 CDN），经典 QQ 表情（微笑、/火车 那些小 id）走腾讯老的
`qzonestyle.gtimg.cn/qzone/em/e{id}.gif`（id ≥ 222 的会动表情腾讯编号是 `10000+id`）。
前端拿不到这两项时会自己按同样规则兜算，所以老后端 / 模拟器也能正常显示。
主持人审核用的那个表情会记在答案记录上，提示里也会带上（`✅ 👍 …已通过审核`）。

后端实现见 ne-danmaku 的 `nekocast_danmaku/danmaku/game_events.py`。

**彩排时确认上游到底推没推这些事件**：打开
`GET /api/danmaku/v1/admin/event-probe?token=<upstream.token>`（`?reset=true` 清空），
看每个事件类型的次数、最后一次的 id、以及后端认不认识它
（`handled: false` = 上游推了但后端没处理）。

### 行内元素（`<face id="339" type="2" platform="llonebot"/>`）——不能带上大屏，一律换成 █

上游会把表情之类的段塞进消息文本里。**游戏只认纯文本**，所以：

- 后端会给每条消息补 `inline`（切好的段，弹幕姬显示页用它行内渲染成图片）和
  `text_plain`（元素整体换成 `█`）；
- 游戏侧优先用 `text_plain`，老后端没给时自己按同样规则替换成 `█`——
  玩家不可能靠标签把图片/卡片塞进答案或昵称带上大屏；
- **只发一个表情也算数**：那条答案就是 `█`（不特殊拒绝）；
- 控制词匹配时元素是**整个剔掉**（不是换成 █），所以群里发
  「开始报名<face/>」也能被认出来（QQ 经常给消息追个表情）；
- `platform` 之类的附加属性不参与任何判断。
